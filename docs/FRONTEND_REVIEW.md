## 1. P1 — отправлять только изменённые поля поручения

**Место:** `frontend/src/components/TaskTable.tsx:161–168`; правила сервера — `backend/app.py:199–224`.

Сейчас `save` отправляет весь draft, включая неизменённые `due_date`, имя исполнителя и `reviewed`. Backend воспринимает наличие полей как явную правку. Это ошибка интеграции: типы запросов совместимы, но изменение статуса затрагивает смысловые поля.

**Воспроизведено в браузере с настоящим API: у поручения «Согласовать бюджет» изменить только статус «Открыто» → «В работе».**

| Поле | До сохранения | После сохранения |
|---|---|---|
| `deadline_text` | «после получения сметы» | Без изменений |
| `deadline_kind` | `event` | `relative` |
| `due_date` | `null` | `null` |
| `review_reasons` | «Срок зависит от события»; «Нужно сверить условия согласования» | Исходные причины потеряны, заменены общими |

**Задача второму участнику:** вычислять PATCH относительно исходных значений при открытии редактора. Если изменён только статус, отправлять ровно `{"status":"in_progress"}`. Не отправлять прежнюю дату как повторное назначение. Явное очищение поля должно отправлять `null`, а неизменённое неизвестное значение — не отправляться. `reviewed` передавать как отдельное осознанное действие; не переносить прежнее подтверждение на изменённый текст автоматически. При отсутствии правок закрывать редактор без PATCH.

Также проверить ситуацию: открыть редактор поручения, переименовать связанного спикера, затем сохранить только статус. Старый draft не должен возвращать прежнее имя исполнителя.

**Приёмка:** тесты для `event`, `conflicting`, `relative`, неизвестной даты, явной очистки даты, смены статуса и повторного подтверждения после смысловой правки. Неизменённые поля и причины проверки сохраняются. Для обычной смены статуса запрос не содержит остальных полей.

**Вклад лидера:** отдельно усилить backend, чтобы повторная передача прежних значений не меняла тип срока. Это дополнительная защита; frontend всё равно должен избегать отправки устаревшего draft целиком.

## 2. P2 — вход и восстановление сессии внутри интерфейса

**Место:** `frontend/src/lib/api.ts:120–155`, обработчики ошибок в `frontend/src/App.tsx:165–184` и `219–220`. В API-клиенте отсутствуют методы работы с `/api/session`.

При первом открытии production backend уже показывает `/login`. Но при истечении cookie в открытой вкладке PATCH получает 401, а интерфейс показывает «Требуется код доступа к приложению» без способа войти. Это воспроизведено удалением тестовой сессии при открытом UI. В разработке Vite также проксирует только `/api`; переход на `/login` dev-сервера не решает вход на backend.

**Задача:** добавить вход по коду через `POST /api/session`, обработку 401 и возможность выхода через `DELETE /api/session`. Токен Hugging Face здесь не используется. Не хранить код в `localStorage` и не включать в сборку; сессию хранит HttpOnly cookie backend. После входа восстановить выбранное совещание и сохранить несохранённый draft. Не повторять POST загрузки автоматически: это может создать дубликат.

**Приёмка:** неверный код; успешный вход; истечение сессии при PATCH; повторный вход без потери правок; ручное сохранение после входа; выход. Проверить на одном origin и через Vite proxy. В документации оставить один origin основным способом развёртывания: при прямом запросе на другой origin текущий `credentials: "same-origin"` не передаёт cookie.

## 3. P2 — показывать уже сохранённый транскрипт при ошибке LLM

**Место:** `frontend/src/App.tsx:706` — весь результат, включая плеер и транскрипт, находится внутри `{ready && (...)}`. Backend сохраняет спикеров и сегменты перед вызовом LLM: `backend/worker.py:46`.

**Воспроизведено:** API возвращает `status=failed`, `stage=extract` и один сохранённый сегмент. UI показывает сообщение о сбое, но не показывает ни этот сегмент, ни аудио. Пользователь теряет доступ к уже выполненной части работы через интерфейс.

**Задача:** отдельно показывать плеер и доступные сегменты при `processing`/`failed`, когда они уже есть. Сохранять видимое сообщение об ошибке и этап. В частичном результате отключить редактирование имён и поручений: API разрешает PATCH только для `ready`. Не показывать пустые поручения как успешно завершённый результат; экспорт оставить недоступным.

**Приёмка:** `failed/extract` с сегментами; `processing/extract` с сегментами; ошибка до распознавания без сегментов; настоящий `ready` без поручений. Состояния должны различаться.

## 4. Интеграционные тесты и передача

Добавить небольшой прогон с настоящим FastAPI и синтетическими сохранёнными данными. GPU для проверки UI/API не требуется. Проверить вход, смену статуса без изменения срока, правку исполнителя, reload, источники, аудио Range и скачивание обоих форматов. Не подменять эти запросы через `page.route`.

Существующие unit/E2E-тесты сохранить. Тесты на моки полезны для ошибок и быстрых проверок, но новая ошибка должна иметь регрессионный тест, который упадёт на текущей реализации. Скриншот красивой страницы не является проверкой сохранения или экспорта.

При передаче прислать лидеру SHA нового коммита и результаты команд:

```bash
cd frontend
npm ci
npx playwright install chromium
npm run build
npm test
npm run test:e2e
```

Работать в `codex/frontend`, менять `frontend/**`, `docs/FRONTEND.md`, `docs/DEMO.md`. Перед интеграцией синхронизироваться с актуальным `main`, который содержит backend и контракт. Не менять backend и смысл полей без согласования с лидером.

## 5. После исправлений — реальные демо-записи

В `docs/DEMO.md` уже подготовлены сценарии RU, KK и смешанной речи. Следующая задача — выполнить их, а не написать ещё один план. Записать короткие обезличенные диалоги с двумя разными голосами; казахский текст и ожидаемые поручения проверить носителем. Использовать реальные результаты модели после готовности сервера лидера.

Зафиксировать: ожидаемые/найденные поручения, лишние и пропущенные, исполнителей, сроки, изменение срока, источники и ошибки голосов. Проверить имя внешнего исполнителя, департамент и срок без даты совещания. Если запись или проверка носителем не выполнены, прямо указать «не проверено».

Порядок работы при ограниченном времени: **частичный PATCH → восстановление сессии → частичный транскрипт → интеграционный прогон → языковые демо**. Дополнительный дашборд, новая анимация и редизайн сейчас уступают этим задачам.
