# Meetora · интерфейс ассистента совещаний

Meetora — продукт команды **Be Like AI**.

Владелец этой части — второй участник. Стек: React, TypeScript, Vite; исходники находятся в `frontend/`. Backend, модели, хранение, вычисление просрочки и формирование PDF/DOCX принадлежат первому участнику.

Meetora помогает секретарю получить **проверяемый проект протокола**: запись → обработка → саммари и реплики → проверка поручений по источникам → сохранение исправлений → экспорт. Поручение без подтверждения или с неясным сроком требует проверки человеком.

## Локальный запуск

Из корня репозитория:

Требуется Node.js 22.20 или новее.

```sh
cd frontend
npm ci
npm run dev
```

`npm ci` устанавливает зависимости по зафиксированному `package-lock.json`. При первоначальном создании или намеренном обновлении зависимостей используется `npm install`; изменённый lockfile нужно сохранить вместе с `package.json`.

Проверка перед передачей:

```sh
npm run test
npm run build
```

Браузерные проверки реального API-клиента с контролируемыми HTTP-ответами:

```sh
npx playwright install chromium
npm run test:e2e
```

Playwright запускает Vite на порту 4173 в режиме настоящего API и подменяет ответы внутри тестового браузера. Проверяются ошибки, загрузка, минимальный PATCH, восстановление сессии, частичный транскрипт, источники и остановка опроса. Это проверка поведения интерфейса; она не заменяет настоящий сервер и не испытывает модели.

Команды выполняются в `frontend/`. Собранные файлы находятся в `frontend/dist/`. Успешная сборка или тест интерфейса сами по себе не подтверждают работу моделей, поддержку языков и экспорт backend.

### Интеграция с настоящим FastAPI без GPU

Из корня репозитория установите зависимости backend в отдельное окружение. Пример для PowerShell:

```powershell
python -m venv frontend/.venv-integration
./frontend/.venv-integration/Scripts/python.exe -m pip install -r requirements-dev.txt
$env:MEETORA_TEST_PYTHON = (Resolve-Path 'frontend/.venv-integration/Scripts/python.exe').Path
cd frontend
npm run test:integration
```

Для Linux/macOS путь к Python в таком окружении — `frontend/.venv-integration/bin/python`; установите им `requirements-dev.txt` и передайте его абсолютный путь через `MEETORA_TEST_PYTHON`. Вместо нового окружения можно указать существующий Python с этими зависимостями. Без переменной используется команда `python`. Предварительно нужны `npm ci` и `npx playwright install chromium` из раздела выше.

`npm run test:integration` собирает frontend и запускает проверки без `page.route` с настоящими FastAPI, SQLite и генераторами документов. Один прогон проверяет собранное приложение на `http://127.0.0.1:8189`, второй — тот же API через Vite proxy на `http://127.0.0.1:4189`. Оба порта должны быть свободны. Проверяются вход, смена статуса без повторной отправки срока, изменение исполнителя, reload, источники, аудио Range и содержимое скачанных PDF/DOCX.

Сервер тестов использует временное хранилище, синтетические совещания и WAV с тишиной; обработчик моделей отключён. Код доступа генерируется только для этого прогона и не попадает в сборку. Такой тест проверяет реальные правила API, cookie и сохранение, но не распознавание речи, диаризацию и извлечение моделью.

## Настройки

Для местных настроек создайте `frontend/.env.local`. После изменения переменных перезапустите Vite; для развёртывания соберите приложение заново — Vite подставляет значения при сборке.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `VITE_USE_MOCKS` | `false` | Только точное значение `true` включает демонстрационные данные |
| `VITE_API_BASE_URL` | не задана | Относительные запросы к `/api` на origin приложения |
| `VITE_PROXY_TARGET` | `http://127.0.0.1:8000` | Backend для Vite proxy `/api` при разработке |

`VITE_API_BASE_URL` принимает origin (`https://meeting.example`) или адрес с префиксом (`https://meeting.example/api`, `/api`). Префикс `/api` не должен дублироваться. Основной способ развёртывания — **один origin**; оставьте переменную незаданной. Запросы используют `credentials: "same-origin"`: прямое обращение браузера к другому origin не передаёт cookie сессии и не поддерживается как схема входа. Для разработки используйте Vite proxy.

Пример для локального backend:

```dotenv
VITE_USE_MOCKS=false
VITE_PROXY_TARGET=http://127.0.0.1:8000
```

`VITE_PROXY_TARGET` применяется только dev-сервером. Не подставляйте адрес `localhost` в production `VITE_API_BASE_URL`: для пользователя это адрес его компьютера. Переменные `VITE_*` доступны браузеру; токены моделей, ключи и приватные сведения в них не помещают.

### Явный режим демонстрации интерфейса

```sh
npm run dev:demo
```

Команда запускает Vite с `--mode demo`; `frontend/.env.demo` задаёт `VITE_USE_MOCKS=true`. На экране постоянно должна быть надпись **«Демонстрационные данные»**. Это обезличенный пример для проверки интерфейса: реальная загрузка, воспроизведение аудио и скачивание PDF/DOCX в этом режиме недоступны и должны быть обозначены как недоступные.

Демонстрационные реплики не являются результатом ASR, разметка говорящих не доказывает акустическую диаризацию. При ошибке настоящего API переход на моки запрещён. Перед проверкой реального конвейера убедитесь, что в окружении и `.env.local` не осталось `VITE_USE_MOCKS=true`.

## Подключение backend

В разработке браузер обращается к Vite, а Vite передаёт `/api/*` на `VITE_PROXY_TARGET`. В production backend или reverse proxy обслуживает `dist` как статические файлы и `/api/*` на **одном origin**. `/api` не должен перехватываться обработчиком статики. Браузер обращается к приложению; доступ к моделям остаётся на сервере.

Адрес выбранного совещания имеет вид `#/meetings/{id}`. После обновления страницы интерфейс берёт идентификатор из hash и загружает сохранённое совещание через API. Hash не отправляется серверу, поэтому отдельный серверный маршрут для каждой страницы совещания не нужен. Сохранность результатов после перезапуска backend обеспечивает backend.

### Вход и восстановление сессии

Владелец backend выдаёт код доступа к приложению. Форма отправляет `POST /api/session` с JSON `{"token":"введённый код"}`; сессию хранит HttpOnly cookie backend. Код не записывается в `localStorage`, не включается в `VITE_*` или сборку и не является токеном Hugging Face. При неверном коде форма остаётся открытой и показывает ошибку.

Ответ `401` в уже открытом интерфейсе вызывает окно входа. После успешного входа остаются выбранное совещание и несохранённые формы поручения, имени говорящего или загрузки в этой вкладке. Повторяются чтения данных; сохранение правки и отправку записи пользователь повторяет вручную. Автоматического повторения `POST /api/meetings` нет, чтобы не создать дубликат записи. Перезагрузка или закрытие вкладки не сохраняет черновики.

Кнопка «Выйти» вызывает `DELETE /api/session` и очищает показанные данные и открытые формы. Это явный выход, а не восстановление истёкшей сессии. Если backend защищает первое открытие приложения страницей `/login`, её обслуживает сам backend; в Vite вход выполняется через окно интерфейса и проксируемый `/api/session`.

Минимальный порядок интеграции:

1. Проверить `GET /api/health`, войти по коду при необходимости, затем открыть список `GET /api/meetings`.
2. Отправить MP3/WAV через `POST /api/meetings` как `multipart/form-data`. Обязательны `file`, `title`, `participants_notified=true`; `timezone` — IANA, по умолчанию `Asia/Almaty`. Если время неизвестно, `started_at` отсутствует; известное передаётся в ISO 8601 с UTC offset.
3. После `202` открыть `meeting_id`. Опрос `GET /api/meetings/{id}` — раз в две секунды до `ready`/`failed`; при уходе со страницы опрос прекращается. Отображать этап и процент из API, не придумывать прогресс при `progress=null`.
4. В состоянии `ready` проверить аудио `GET /api/meetings/{id}/audio` с поддержкой Range, реплики, поручения и источники.
5. Проверить PATCH имени говорящего и PATCH поручения. Ответ — сохранённый объект; ошибка не должна выглядеть как успешное сохранение.
6. Скачать `GET /api/meetings/{id}/export?format=pdf` и `format=docx`, открыть оба документа и сверить сохранённые правки.

## Правила данных и состояний

- Неизвестные значения — `null`, коллекции — `[]`; пустое поручение или саммари не подменяются демонстрационным текстом.
- Говорящий и исполнитель различаются. Внешний человек или подразделение могут быть исполнителями без `assignee_speaker_id`. Исправление имени спикера не назначает ему поручения из его реплик.
- Неизвестное имя показывается как «Спикер 1» или предоставленный backend аналог. Цвет реплики помогает различать голоса, но не подтверждает личность.
- Исходный `deadline_text` сохраняется. «После совещания», «на следующей неделе», «15 октября» без года и конфликт сроков не превращаются автоматически в сегодняшнюю дату.
- `is_overdue` вычисляет backend в часовом поясе совещания. День срока включительно не является просрочкой; для неопределённого срока дата не выдумывается.
- «Источник» использует только `evidence_segment_ids`: прокручивает к подтверждающей реплике и ставит аудио на её `start`. Отсутствующие ID явно обозначаются; случайная реплика не заменяет источник. Несколько источников нужно сохранить, включая уточнение срока.
- Ошибки `error.message`, FastAPI `detail`, сетевые сбои и ошибки скачивания должны быть видны пользователю. Для `failed` показываются причина и последний известный этап.
- Если при `processing` или `failed` уже сохранены сегменты, доступны аудио, таймкоды, поиск и транскрипт. Это явно обозначенный частичный результат: причина сбоя или текущий этап остаются видимыми; имена говорящих и поручения не редактируются. До `ready` не показываются итоговое саммари и пустое состояние «Поручения не найдены». Ошибка до появления сегментов не создаёт пустой транскрипт как результат.
- Экспорт разрешён только для `ready`. Несохранённые исправления необходимо сохранить до скачивания; документ создаётся backend из последней сохранённой версии. Неоднозначности не скрываются.

### PATCH поручений и подтверждение проверки

Редактор сравнивает поля со снимком поручения при открытии и отправляет только изменения. Например, смена «Открыто» на «В работе» отправляет ровно `{"status":"in_progress"}`. Неизменённые срок, имя исполнителя и `reviewed` не отправляются. Это также не позволяет старому черновику вернуть прежнее имя исполнителя после переименования связанного говорящего. При отсутствии изменений редактор закрывается без PATCH.

Явное очищение ранее заданной даты или имени отправляет `null`; неизменённое неизвестное значение в запрос не включается. Исходные `deadline_text`, `deadline_kind` и причины проверки определяет backend, frontend их не перезаписывает черновиком. Полученный ответ сервера становится сохранённым состоянием.

`reviewed` передаётся только после осознанного действия с флажком. Смысловая правка текста, исполнителя или даты сбрасывает подтверждение в редакторе: для подтверждения изменённого поручения флажок нужно установить заново после последней такой правки. Одно изменение статуса повторного подтверждения не требует. Серверные причины проверки отображаются по ответу API и не скрываются только из-за флажка.

## Замечание владельцу backend (`main` на `d50bdf0`)

Изолированной проверкой настоящего FastAPI подтверждено: если у поручения `reviewed=true` и остались `review_reasons`, даже PATCH `{"status":"in_progress"}` очищает исходные причины в `backend/app.py` (ветка `if task.reviewed`). Для событийного срока без календарной даты после этого остаётся только общая причина «Календарный срок не определён». При `reviewed=false` исходные причины сохраняются, но сервер дописывает эту общую причину.

Frontend теперь отправляет только изменённые поля и не может сохранить причины, которые сервер сам удалил: `review_reasons` отсутствует среди разрешённых PATCH-полей. Требуется отдельная правка владельца backend: изменение статуса не должно переоценивать смысловые поля и причины проверки. Код backend в рамках этих исправлений не изменялся.

## Границы готовности

Фронтенд не реализует ASR, диаризацию, модели, GPU-обработку и генерацию документов. Работа экрана на моках не означает готовность backend. Фактическую поддержку русского, казахского и смешанной речи фиксируют только после отдельного сквозного прогона; методика и сценарий защиты находятся в [DEMO.md](DEMO.md).

Teams/Zoom/Meet, внешняя рассылка и СЭД не входят в реализуемый за пять часов основной путь. Сведения в анализе о GPU и кандидатах моделей — исходный контекст команды, а не подтверждение текущего состояния сервера.
