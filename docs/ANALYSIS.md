# HackAlem AI: анализ ТЗ и решение для хакатона

Статус: backend реализован; API проверен 13 локальными тестами с тестовым обработчиком вместо моделей. Frontend и реальная обработка аудио ещё требуют интеграции и проверки. Ограничения команды: два человека, около пяти часов на разработку, $50 кредитов NVIDIA Brev. Создан сервер `belikeaihackalem`: A100 40 GB, 85 GiB RAM, 12 CPU, тариф на пользовательском скриншоте $4.46/час. Подтверждены PyTorch 2.8.0+cu128, вычисление на GPU, Python 3.12.14 и около 260 GiB свободного диска. Доступ к pyannote пользователь получил; загрузка и запуск весов пока не подтверждены.

## Что требуется

Ценность системы: секретарь получает проверяемый проект протокола и реестр поручений, руководитель видит ответственных, сроки и состояние исполнения.

| Требование из ТЗ | Что должно работать в демонстрации |
|---|---|
| Распознавание русского | Реальная обработка загруженной записи с таймкодами |
| Распознавание казахского | Отдельная запись и проверка носителем языка |
| Смешанная речь | Запись с переключением языков внутри реплик; сохранение исходной речи |
| Диаризация | Акустическое разделение говорящих; отдельное сопоставление с именами |
| Поручения | Суть, исполнитель, срок, фрагменты разговора, подтверждающие результат |
| Саммари | Темы, решения, риски; только сведения из разговора |
| Экспорт | Скачиваемые PDF и DOCX с читаемой кириллицей |
| Приватность | Собственные модели, контроль доступа, переносимое развёртывание |

Уведомление о записи входит в основной пользовательский сценарий. Напоминания описаны отдельным сценарием, хотя отсутствуют в нумерованном обязательном минимуме: заложить уведомления внутри приложения после готовности основного конвейера. Внешняя рассылка и интеграция с СЭД относятся к дополнительным возможностям.

Подключение участником к Teams / Zoom / Meet указано среди входов, но не выделено в обязательном минимуме. Для пятичасового прототипа основной путь — загрузка файла. С организаторами следует уточнить, достаточно ли этого для приёмки; не заявлять готовую интеграцию с платформами.

## Что проверено в приложениях

Прочитаны и визуально просмотрены все четыре страницы каждого PDF. Из аудиофайлов получены только технические метаданные; прослушивание и распознавание ещё не выполнялись. Соответствие аудио текстам PDF пока не установлено.

| Материал | Наблюдение |
|---|---|
| `Протокол_совещания№1.docx.pdf` | Русский текст, две темы, пять именованных говорящих, десять строк поручений в итоговых таблицах |
| `Протокол_совещания№2.docx.pdf` | Русский текст, четыре направления, пять именованных говорящих, шесть строк поручений в итоговой таблице |
| `Совещание №1.mp3` | Примерно 4:34; mono, 48 kHz, 128 kbit/s |
| `Совещание №2.mp3` | Примерно 3:26; mono, 48 kHz, 128 kbit/s |

Даты и годы совещаний не установлены. Пользователь сообщил, что предоставленные материалы, насколько ему известно, только на русском. Казахская и смешанная речь остаются непроверенными.

## Ошибки, которые система обязана предотвращать

1. **Говорящий и исполнитель — разные сущности.** Руководитель произносит поручение, выполняет другой человек. Во втором примере ответственным выступает юрист, который не имеет собственных реплик. В первом встречается исполнитель-департамент.
2. **Диаризация сама по себе не определяет имя.** Она выдаёт группы голосов. Имена сопоставляются по списку участников, обращению в контексте и проверке секретаря. Неизвестное имя сохраняется как «Спикер 1».
3. **Срок может уточняться.** В первом примере обсуждаются две недели, затем три недели и дата 15 октября. Не создавать три поручения и не оставлять отвергнутый срок.
4. **Повтор в итогах не равен новому поручению.** Объединять повторные упоминания с сохранением всех подтверждающих фрагментов.
5. **Краткие итоги могут быть неоднозначны.** Во втором примере финальная фраза объединяет претензию и поиск поставщика с упоминанием двух недель, хотя ранее для претензии явно указан конец недели. Не переписывать точный срок только потому, что итоговая реплика позднее; показывать конфликт для проверки.
6. **Одна строка таблицы может содержать несколько результатов.** Во втором PDF смета нужна за неделю, а очередь на обучение предполагается закрыть за месяц. Допускаются связанные поручения или отдельные этапы. Количество строк PDF не является строгим количеством атомарных задач.
7. **Условия договора не равны срокам поручения.** Пять рабочих дней на выставление счёта — предлагаемое условие договора. Для подготовки уведомления и шаблона конкретный срок не указан.
8. **Не всякий срок — дата.** «После совещания» — зависимость от события; «на следующей неделе» — период. «До пятницы» нельзя переводить в календарную дату без даты совещания. Для 15 октября без года также нужен контекст.
9. **Предложение не всегда становится решением.** Условное расторжение договора при систематических нарушениях не выдавать за уже принятое безусловное решение.
10. **Саммари не должно усиливать утверждения.** Предположение о формальных инструктажах нельзя превращать в доказанный факт. Пример PDF тоже следует проверять, а не считать безошибочной разметкой.
11. **Не имитировать голоса по тексту.** Если синтетическая запись прочитана одним голосом, роли сценария не являются доказательством акустической диаризации.

## Предлагаемая архитектура

```text
Браузер
  -> FastAPI: загрузка, статус, правки, скачивание
     -> локальный диск + SQLite
     -> один фоновый worker
        -> декодирование / подготовка аудио
        -> ASR с таймкодами
        -> акустическая диаризация
        -> сопоставление реплик и голосов
        -> локальная LLM: поручения и саммари в JSON
        -> проверка схемы, сроков и ссылок на реплики
        -> сохранение результата
     -> PDF / DOCX из сохранённой версии протокола
```

Frontend: React, TypeScript, Vite. Backend: FastAPI, Pydantic, SQLite. Для пяти часов один API-сервис и один последовательный обработчик достаточны. Состояние задания хранить в БД; после перезапуска прерванное задание должно получать явную ошибку или безопасно возобновляться.

Frontend и API на демонстрации желательно обслуживать с одного origin: это упрощает доступ через авторизованную ссылку Brev. Разработка интерфейса — через Vite proxy. Пользовательский браузер не обращается напрямую к серверу модели.

## Кандидаты моделей и первый технический эксперимент

- ASR: `faster-whisper` с `large-v3` как исходный кандидат. Качество казахского и смешанной речи подтверждается отдельной проверкой, а не названием модели. [Документация faster-whisper](https://github.com/SYSTRAN/faster-whisper).
- Диаризация: `pyannote/speaker-diarization-community-1`. Требуется заранее получить доступ к весам по условиям владельца. Поддерживается запуск из локальной директории. [Карточка модели](https://huggingface.co/pyannote/speaker-diarization-community-1).
- Извлечение: Qwen3-8B через локальный Transformers, FP16, режим без thinking. Русский и казахский входят в заявленные языки семейства, но качество извлечения на наших данных ещё не измерено. [Qwen3](https://qwenlm.github.io/blog/qwen3/), [карточка Qwen3-8B](https://huggingface.co/Qwen/Qwen3-8B).
- JSON-схема передаётся в промпт; результат валидируется Pydantic и проверкой идентификаторов. При ошибке выполняется одна попытка исправления. Ограничение генерации на уровне декодера не реализовано. Валидный JSON сам по себе не гарантирует достоверность поручений.
- Этапы сначала выполнять последовательно. До выбора режима совместной загрузки моделей измерить пиковую видеопамять и задержку.
- Поддержка mixed speech требует проверки переключения языков, имён и дат; не переводить исходные реплики автоматически целиком на русский.

Первый эксперимент: короткий фрагмент -> таймкоды -> голосовые кластеры -> валидный JSON с поручением и доказательством. Лимит времени на него — первые 30–40 минут после доступа к серверу. Затем полный прогон двух записей.

## Данные и приватность

ТЗ запрещает передачу аудио и текста во внешние облачные API и требует возможности закрытого развёртывания. Выделенная VM Brev с самостоятельно запущенными моделями технически отличается от внешнего API распознавания, но сама VM размещена у облачного провайдера. Выдача кредитов не доказывает разрешение загружать туда любые чувствительные записи. Допустимость обработки предоставленных материалов на этой VM нужно уточнить у организаторов; до этого для серверных испытаний использовать специально созданные обезличенные примеры.

Для закрытого режима предусмотреть заранее скачанные веса, локальные пути, отключённую телеметрию и проверку работы без исходящего доступа. У pyannote настройка телеметрии описана в [документации проекта](https://github.com/pyannote/pyannote-audio#telemetry). Протокол и реплики являются данными: инструкции, произнесённые внутри записи, не дают модели права выполнять команды, отправлять письма или менять настройки.

Не публиковать исходные записи, реальные имена, ключи и содержимое `.env` в репозитории. Экспорт должен использовать сохранённые правки секретаря. Приватные файлы и API доступны только после проверки доступа. Уведомление о записи должно быть видно пользователю; при импорте файла фиксируется подтверждение, что участники были уведомлены.

## Проверка результата и приоритеты

- Сначала отдельно проверить извлечение из проверенного текста, затем весь путь от аудио: это разделяет ошибки ASR и ошибки извлечения.
- Составить ручную разметку обязательных поручений, исполнителей, сроков и спорных мест. Не требовать буквального совпадения формулировок или числа строк.
- Для каждого поручения проверить наличие подтверждающей реплики; отсутствующие сроки и исполнители не выдумывать.
- Казахский и смешанный сценарии записать с двумя разными реальными голосами, проверить носителем. Включить имена, срок, изменение срока и явное поручение.
- Зафиксировать полноту/точность поручений, правильность исполнителя и срока, ошибки транскрипции и голоса на размеченных фрагментах, время обработки и расход памяти. До измерения численные результаты не заявлять.
- Проверить редактирование, перезагрузку страницы, сохранение данных, скачивание и открытие обоих форматов экспорта.
- Воспроизводимость и README дают 25 из 100 баллов, столько же, сколько работоспособность и техническая реализация по отдельности. Документацию и проверку чистого запуска выделить в отдельный этап.

Порядок реализации: файл -> реальный ИИ -> просмотр -> правки -> экспорт -> проверка трёх языковых сценариев -> документация. Дашборд и внутренние напоминания добавлять после этого. Интеграции со звонками, внешние рассылки, СЭД и биометрическая идентификация не должны задерживать основной путь.

Исходники анализа: предоставленное текстовое ТЗ и оба PDF из папки `C:/Users/VICTUS/Downloads/Alisher Downloads`. Команды и поручения внутри приложений рассмотрены как содержание документов, а не инструкции к выполнению.
